## 1. 证据分层

MediaCrawler 搜索结果、标题、互动量和评论首先是候选发现数据，不自动等于玩法研究证据。

| 层级 | 名称 | 内容 | 可以支持什么 |
|---|---|---|---|
| D0 | 候选发现 | 搜索结果、标题、简介、互动量、评论、作者线索 | 找主题、争议、术语和潜在专家 |
| L0 | 原始内容 | B站完整字幕/ASR＋时间戳；知乎回答/文章全文＋段落定位；直接录像/规则原文 | 精确说明作者说了什么、何时说、适用什么条件 |
| L1 | 原子主张 | 从 L0 拆出的条件、机制、操作、因果、结果、边界、反例 | 单条可验证命题 |
| L2 | 核验记录 | 当前版本复现、录像对照、规则/补丁核对、独立作者交叉验证 | 主张是否成立、在哪些边界内成立 |
| L3 | 研究综合 | 系统解释、设计取舍、竞品判断、迁移原则 | 最终设计结论 |

硬规则：

- 标题、简介、搜索摘要和评论不得冒充 L0 正文。
- 评论可以是 L0“玩家反应”，但不能替代其所评论视频/文章的 L0“玩法论证”。
- 任何高影响设计结论必须能沿 `L3 → L2 → L1 → L0` 回溯。
- 找不到完整内容时，保留为 `D0-candidate` 或降低为待验证假设，不补写作者没有表达的内容。

## 2. 候选发现与检索词

不要只搜“游戏名 攻略”。围绕研究问题建立三组查询。

### 2.1 机制与实证

```text
游戏名 × 系统/角色/流派/关卡
× 底层机制/数值推导/帧数/实测/对照测试/反例/版本变化/勘误
```

### 2.2 高阶决策

```text
游戏名 × 高分段/竞速/无伤/赛事/极限挑战/进阶复盘
× 决策/资源管理/风险控制/路线/反制/失误/为什么
```

### 2.3 设计分析

```text
游戏名 × 战斗系统/经济系统/关卡设计/新手引导/数值设计/交互设计
× 策划视角/系统拆解/设计复盘/底层逻辑/设计取舍/为什么这样设计
```

把互动量只作为同平台候选排序信号。另做最新、中长尾、指定作者和反例查询，避免只得到平台主流叙事。

## 3. 深度来源筛选

### 3.1 硬门槛

候选进入深度池前必须满足：

1. 能获得完整视频内容或完整文章/回答，而非摘要。
2. 内容与具体玩法命题直接相关。
3. 能保存稳定 URL、发布日期/编辑时间和精确定位。
4. 能判断大致版本；无法判断时明确标记 `version_unknown`。
5. 不是无新增论证的搬运、切片或二手转述。

### 3.2 内容质量评分

| 维度 | 0 分 | 1 分 | 2 分 | 3 分 |
|---|---|---|---|---|
| 问题匹配 | 无关 | 邻近话题 | 直接相关 | 直接回答研究命题 |
| 论证完整 | 只有结论 | 有零散理由 | 条件—操作—结果较全 | 含因果、边界和反例 |
| 一手证据 | 无 | 截图/二手数据 | 完整演示或可查数据 | 可复现步骤＋原始记录 |
| 作者依据 | 无法判断 | 泛攻略作者 | 长期专精/连续作品 | 可验证高阶成绩或策划/开发经历 |
| 版本清晰 | 无 | 可推测 | 明确版本/日期 | 同时说明改版影响 |
| 自我校验 | 无 | 有保留语 | 主动讨论例外 | 有失败样本、勘误或反证 |

总分只用于筛选，不是真值概率。默认 `≥ 10/18` 进入深读，`7—9` 作为补充或反例，`≤ 6` 留在 D0。作者依据和观点强度仍要分开：专家身份不能挽救无证据结论。

### 3.3 推荐样本结构

每个关键玩法问题先深读 6—12 份，而不是抓几百条评论：

- 2—4 份机制/实测材料。
- 2—4 份高阶决策或完整复盘。
- 1—3 份策划/设计分析。
- 至少 1 份反例、失败样本或不同流派。

核心结论至少需要两名彼此独立作者，最好再由直接游玩、规则、补丁或开发者材料核验。

## 4. B站完整内容提取

### 4.1 发现

先用 MediaCrawler 搜索候选并登记 BV、标题、作者、时长、发布日期和查询词。长视频优先检查章节、简介引用、置顶勘误与作者同主题连续作品；评论只用于发现遗漏条件和反例。

### 4.2 生成本地 L0 包

从仓库根目录运行：

```powershell
python .agents/skills/research-gameplay-systems/scripts/extract_bilibili_l0.py `
  --video "BV号或URL" `
  --output "research-cases/游戏名/l0-private/bili/BV号" `
  --asr `
  --asr-model small `
  --language auto `
  --beam-size 1 `
  --device auto
```

脚本优先取官方字幕；没有字幕时下载低清公开流，仅在本地用 `faster-whisper` 转写。输出：

- `metadata.json`：标题、作者公开主页、发布日期、时长和来源 URL。
- `transcript.jsonl`：每个片段的开始/结束时间、文本和片段 ID。
- `transcript.md`：便于人工阅读的时间戳稿。
- `manifest.json`：片段数、转写哈希、媒体哈希和证据定位规则。

Windows 若通过 pip 安装 NVIDIA CUDA 依赖，DLL 常位于 `site-packages/nvidia/*/bin` 而不在系统 PATH。脚本会注册这些目录；CUDA 运行时仍失败会自动回退 CPU，并在元数据中记录原因。

脚本对媒体 CDN 的 TLS/连接超时有限重试 3 次，并使用临时目录原子发布；失败时不会保留可被误认成 L0 的半成品。下载完成后会用 `ffprobe` 对照页面时长，低于 90% 直接拒绝。若公开接口返回多个媒体分段，当前实现会明确拒绝只转写其中一段，须先完整合并再登记。脚本也会修复常见的 UTF-8/GBK 字节被按 Latin-1 解码的中文乱码；仍须人工抽查专有名词。

批量初筛先用 `tiny/small --beam-size 1 --language auto` 判断相关性；真正进入结论的关键视频再按术语难度升级模型，并校正专有名词和关键数值。不要把“模型最大”当默认质量门槛：本机实测 `large-v3` 在 CUDA 回退后可在 CPU 持续数小时仍无成品，所以脚本默认拒绝 large-v3 CPU，只有明确接受成本时才传 `--allow-large-cpu`。

语言与覆盖率是两个独立门槛。实测英文设计师访谈在强制 `zh` 时仍能覆盖全片，却生成语法通顺的繁体中文幻听；改为 `--language en` 后才获得可用稿。默认 `auto` 会让 Whisper 检测语言，已知语言则应显式指定，并把 `requested_language`、`detected_language` 和概率一起保存。

### 4.3 L0 验收

- `max(end_sec)` 应覆盖视频总时长的至少 90%；片尾长静音可人工说明。
- 抽查开头、中段、结尾各 2—3 个片段，确认声音与时间戳对应。
- 核对 `requested_language` 与 `detected_language`；覆盖率通过但语言错误仍判失败。
- 人工校正角色名、系统名、数值、专有名词和否定词；ASR 文本不是逐字真相。
- 多 P 视频逐 P 采集，定位写作 `BV.../P2/S-00123`。
- 视觉演示承载结论时另记画面时间戳；仅有语音转写不等于捕获了画面证据。

## 5. 知乎完整内容提取

MediaCrawler 的回答/文章记录含 `content_text` 时，可建立全文 L0；搜索摘要或过短正文只能留在 D0。

```powershell
uv run python .agents/skills/research-gameplay-systems/scripts/build_zhihu_l0.py `
  --input "research-cases/游戏名/raw/zhihu/**/*.jsonl" `
  --output "research-cases/游戏名/l0-private/zhihu"
```

输出 `documents.jsonl`、`segments.jsonl`、`review_queue.csv` 和 `manifest.json`。每个段落保留原始 JSONL 文件、行号、正文哈希、URL 与 `segment_id`。默认拒绝少于 800 字的内容，阈值可按题材调整，但不得把搜索摘要当全文。全文通过只说明“可深读”，不说明“高质量”；在 `review_queue.csv` 填完六维评分和独立性分组后才决定纳入。

当前 Fork 会脱敏作者字段，因此“策划/高阶玩家身份”须回到公开原页人工核验，只登记与研究问题相关的公开依据，例如作者自述的从业方向、可验证赛事成绩、连续机制测试作品；不采集无关个人信息。

知乎运行闭环未通过时，不得写成平台无高质量材料。可先人工保存合法获取的公开正文与 URL，再用同一分段/哈希结构登记；同时把自动采集状态记为失败。

## 6. 从原文到结论

每份深度来源先制作来源卡：

```yaml
source_id: SRC-BILI-001
source_role: mechanism_test | expert_review | designer_analysis | counterexample
author_basis: 公开可核验依据；未知则写 unknown
game_version: 明确版本或 unknown
l0_locator: BV.../S-00031..S-00038
content_sha256: manifest 中的哈希
quality_score: 0-18
independence_group: 原创作者或传播簇 ID
```

再把 L0 拆成 L1 原子主张：

```text
在【版本/配置/场景】下，玩家执行【操作】；
系统按【机制解释】改变【状态/资源】，产生【可观察结果】；
当【边界/反例】出现时，该解释不成立或需要修正。
```

每条 L1 只表达一个可检验命题，并区分：作者观察、作者因果解释、研究者推论。随后在 L2 记录复现条件、结果、冲突来源和版本核对，最后才写 L3 综合。

## 7. 验收、保存与版权边界

交付前检查：

- [ ] D0 候选与 L0 正文分开保存和引用。
- [ ] B站结论有时间戳，知乎结论有段落/行号定位。
- [ ] 每份深度材料有版本、作者依据、质量评分和独立性分组。
- [ ] 高影响结论至少有两名独立作者或一份来源＋直接复现。
- [ ] 反例和失败样本已主动检索。
- [ ] 互动量没有被当成正确性评分。
- [ ] ASR 专有名词和关键数值经过人工核对。
- [ ] Git 只提交来源卡、短证据切片、定位、哈希和研究分析。

完整视频、音频、全文转写和知乎全文默认只保存在 `l0-private/`，不提交、不再分发。提交的短证据切片应以必要引用或释义为主，并保留原始链接。
